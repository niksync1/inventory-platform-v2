LIVE DATABASE AUDIT AGAINST MIGRATIONS 00200, 00300 AND 00400
Date: 2026-09-15

RESULT
======
One confirmed migration-stopping conflict exists. No current data blockers were
found. Several security and behavioral gaps should be addressed before applying
these migrations.

The live PostgreSQL 17.6 database was inspected through read-only Supabase MCP
catalog queries and aggregate data queries. The database role was
supabase_read_only_user, with RLS bypass, so counts were not filtered by policies.
No database changes, migration applications, or RPC executions were performed.
No repository files were edited during the audit. This report was subsequently
saved at the user's request. This was a catalog/data inspection and SQL review,
not an execution rehearsal. Findings describe the state observed during the audit.

1. EXACT CONFLICTS AND MIGRATION COMPATIBILITY
============================================

CONFIRMED BLOCKER: DUPLICATE CHECK-CONSTRAINT NAME
Location: 00200, lines 268-269

  alter table public.products
    add constraint products_stock_quantity_nonnegative
    check (stock_quantity >= 0);

Live already contains the validated constraint:

  CONSTRAINT products_stock_quantity_nonnegative
  CHECK (stock_quantity >= 0)

Adding another constraint with this name on products will fail.

Recommendation: Preserve the existing constraint. Remove the redundant statement
for the verified baseline, or check its table, name, definition and validation
state before conditionally creating it. Do not silently accept a same-name
constraint with a different definition.

OTHER OVERLAPPING NAMES ARE HANDLED CORRECTLY
- 00200:232-236 drops five global unique constraints. All five exist with the
  expected columns. Compatible.
- 00200:244-247 drops four old indexes. All four exist. Compatible.
- 00200:266-267 sets stock default 0 and NOT NULL. Both already set; redundant
  but harmless.
- 00200:271-274 replaces profiles_role_check. Live permits warehouse and admin;
  existing values remain valid under the replacement.
- 00300:94 replaces handle_new_user(). Same arguments and trigger return type;
  compatible.
- 00300:108-111 replaces on_auth_user_created. Existing trigger explicitly handled.
- 00300:146-147 drops old stock RPCs. Exact signatures exist; no catalog
  dependencies found. Compatible database change, but breaking client API change.
- 00300:68 creates can_manage_inventory(uuid). Live has can_manage_inventory().
  This creates an overload; it does not replace the legacy function.
- 00400:1-12 drops legacy policies. All 12 named policies exist. Compatible.

No live relation/type names conflict with the six new tables: tenants, locations,
tenant_memberships, platform_admins, customers, inventory_levels.
New tenant/customer/location columns, new index names, new constraint names other
than the stock check, and new policy names are absent live. Other new RPC
signatures are absent.

3. SECURITY DISCREPANCIES AND RECOMMENDED CHANGES
===============================================
The following are gaps in the proposed final state, not migration execution errors.

A. CUSTOMERS CAN EDIT OWNERSHIP AND BUSINESS FIELDS
SQL: 00400:96-103, 136-137.
Self-update checks only auth_user_id = auth.uid(), while table-level UPDATE covers
every column. Customers can change tenant_id where FKs permit and fields such as
buyer_type.
Recommendation: Column grants for self-service fields and a separately authorized
RPC for manager operations, or a trigger enforcing immutable ownership and
protected fields. RLS alone does not restrict which columns change.

B. PRODUCT MANAGERS CAN EDIT AGGREGATE STOCK DIRECTLY
SQL: 00400:18-24, 136-137; conflicts with stock model in 00200:298-299.
Inserts can supply nonzero stock_quantity. Updates can change it without updating
inventory_levels or recording transactions.
Recommendation: Restrict product writes to non-stock fields, enforce initial zero
stock, and require stock changes through stock RPCs.

C. FUTURE FUNCTIONS RETAIN DEFAULT PUBLIC EXECUTION
SQL: 00400:153.
Revoking explicit defaults from anon and authenticated does not remove
PostgreSQL's default PUBLIC EXECUTE.
Recommendation: Add the following without IN SCHEMA, and retain schema-specific
explicit-role revocations. Review the broader scope deliberately.

  ALTER DEFAULT PRIVILEGES FOR ROLE postgres
    REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;

D. TENANT ADMINS CAN EDIT SUBSCRIPTION-CONTROL FIELDS
SQL: 00400:53-56, 138; 00300:14-31.
UPDATE covers status and plan, not just display information. Authorization helpers
do not inspect tenant status.
Recommendation: Restrict subscription/status changes to trusted operations. If
suspension must block access, enforce allowed tenant status in authorization
helpers and public-catalog access.

E. AUTHENTICATED STAFF CANNOT SELECT INACTIVE PRODUCTS/CATEGORIES
SQL: 00400:14-41.
Only active-public SELECT policies are created. UPDATE policies do not supply
staff SELECT visibility.
Recommendation: Add tenant-member or manager SELECT policies including inactive rows.

F. TRACKING/ORDER TENANT CONSISTENCY LACKS A COMPOSITE FK
SQL: 00200:201-203.
Existing order_id -> orders(id) remains alongside a separate tenant FK.
Recommendation: Add UNIQUE (tenant_id,id) on orders and a matching tracking
(tenant_id,order_id) FK. Decide explicitly whether null order_id remains valid.

PUBLIC CATALOG EXPOSURE REQUIRES AN EXPLICIT DESIGN DECISION
SQL: 00400:14-17 and 29-31:

  using (is_active and tenant_id is not null)

Since tenant_id becomes NOT NULL, anyone can read every active product/category
across every tenant. Table SELECT grants expose every column, including stock
and metadata. This matches the policy names but does not provide tenant-scoped
catalog confidentiality. Define which fields and tenants are publishable if
public storefront access is intended. Client-side filtering is not authorization.

EXISTING LIVE SECURITY POSTURE
- All seven public tables grant anon, authenticated and service_role SELECT,
  INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER and MAINTAIN.
- RLS limits ordinary row operations, but grants are broader than necessary;
  RLS does not protect TRUNCATE.
- All eight public functions grant EXECUTE to all three roles. Six also grant
  EXECUTE to PUBLIC (all except the two stock RPCs).
- service_role bypasses RLS; anon and authenticated do not.
- All three roles have schema USAGE and lack schema CREATE.
- No column-specific ACLs were found.
- 00400:131-150 substantially tightens table/function permissions and leaves
  service-role privileges intact.

REMAINING CLEANUP AND HARDENING
- Legacy is_admin() and can_manage_inventory() survive. 00400 removes their
  PUBLIC/anon/authenticated execution and drops dependent admin policies.
  Remove obsolete helpers after dependency and client review.
- Most live/proposed security-definer functions use search_path = public. API
  roles cannot CREATE there, reducing immediate risk. Prefer fully qualified
  references with a trusted path explicitly placing pg_temp last, or an empty
  path with qualification throughout.
- Live supabase_admin defaults also grant broad public-schema privileges.
  00400 changes only postgres defaults; other creator roles remain outside it.
- The legacy profiles policy "System can insert profiles" allows self-ID
  insertion without restricting role. 00400 revokes INSERT, making it ineffective
  for API roles. Drop the obsolete policy to avoid later accidental reactivation.
- 00400:131 removes public.users access with no replacement grant. Its SELECT
  policy remains but becomes ineffective for API roles. Confirm clients moved
  to customers.
- Between separately committed migrations, old broad policies/defaults remain
  until 00400. New RPCs initially inherit broad execution. Tighten grants alongside
  creation and plan a coordinated application cutover.

RPC BEHAVIORAL ISSUES
SQL: 00300:173-178 and 253-258.
Idempotency checks return success for any existing operation ID within the tenant
without checking product, location, quantity or operation type.
Concurrent duplicate requests can both pass the initial check. The unique index
prevents duplicate committed transactions, but one request can fail instead of
returning an idempotent success.
Recommendation: Validate request equivalence and serialize/claim operation IDs
safely. Reject null p_transaction_type explicitly at 00300:250; the current test
lets it reach the table's NOT NULL failure.

RECOMMENDED ORDER OF LOCAL CHANGES
=================================
1. Remove or definition-check the duplicate stock constraint in 00200.
2. Protect customer ownership/business fields and product stock from unrestricted
   column updates.
3. Fix default PUBLIC function execution in 00400.
4. Add staff visibility for inactive catalog rows.
5. Enforce tracking/order tenant consistency.
6. Define public-catalog exposure and tenant suspension/subscription permissions.
7. Harden RPC idempotency, remove obsolete authorization objects, and coordinate
   the API cutover.

The live data currently supports the proposed backfill. The duplicate constraint
and proposed authorization gaps are reasons to revise local migrations before
applying them.
